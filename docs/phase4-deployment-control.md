# Phase 4 Public Beta deployment control preparation

This file prepares a later, separately authorized deployment. It is not permission to migrate, deploy, send Telegram messages, or enable Beta. The final release SHA and tag must be approved after this control change is reviewed.

## Exact migration control

Run with Node 22 from a clean checkout at the reviewed release commit. Supply `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `PHASE4_LOOKUP_KEY`, and `PHASE4_AUDIT_KEY` securely in the operator environment. The latter two are stable, distinct hex keys of at least 32 bytes; the migration may create keyed durable authority, so never rotate them to recover from a failure. The script neither loads `.env` nor prints values. It checks the actual target host, current commit and clean tree, schema range, reshaped tables, integrity and FK state. `--preflight` is read-only. `--apply` verifies v31 postconditions, preserved row counts, locale UNSET for pre-v31 users, no LIVE state, no Body Energy rows on a v20 start, and integrity/FK after the migration. A rerun is supported.

```sh
node scripts/phase4-migrate.js --preflight --expected-target whoop-briefing-enjoyfulwen0204-eng.aws-ap-northeast-1.turso.io --expected-commit REVIEWED_RC_SHA
node scripts/phase4-migrate.js --apply --expected-target whoop-briefing-enjoyfulwen0204-eng.aws-ap-northeast-1.turso.io --expected-commit REVIEWED_RC_SHA --confirm-production whoop-briefing
```

These commands are **not** to be run until Render database identity matches this Turso host, a management-level backup branch and restore path are verified, writers are quiesced, and the final migration is authorized. The generic `npm run migrate` does not inject Phase 4 keys and is not the production migration entry. Startup paths also call `db.migrate()`, so a v31-compatible webhook release must not start on v20 before this controlled migration.

## Required provider transition

1. Read actual Render service ID, source, deployed SHA, branch, build/start commands, Node runtime, plan, auto-deploy, health path, environment-name presence, and the configured `TURSO_DATABASE_URL` hostname. Prove it equals the host above without exposing any token. Freeze auto-deploy before pushing this branch if it is linked to Render.
2. Read actual Cloudflare Worker deployment, bindings and schedules. The reviewed Wrangler target is `*/10 0-3 * * *` with `BRIEFING_ENDPOINT_URL=https://whoop-telegram-webhook.onrender.com/internal/briefing/run` and a separately stored `BRIEFING_TRIGGER_SECRET`. Live identity and endpoint must be verified before deployment. Pause old cron via Dashboard **Workers & Pages → whoop-briefing-scheduler → Triggers → delete current Cron Trigger**, or `PUT /client/v4/accounts/{account_id}/workers/scripts/whoop-briefing-scheduler/schedules` with JSON body `[]`; verify with the corresponding `GET`. Cloudflare documents up to 15 minutes of propagation. Later deploy the reviewed Wrangler config and verify the GET list contains only `*/10 0-3 * * *`.
3. On GitHub, disable `.github/workflows/briefing.yml` before migration via **Actions → WHOOP 早晨簡報 → ⋯ → Disable workflow** or `PUT /repos/enjoyfulwen0204-eng/whoop-briefing/actions/workflows/briefing.yml/disable`. Check workflow state and list its queued/in-progress runs; disabling does not terminate a running job. After the reviewed pinned-SHA workflow lands on default-branch `main`, enable with the corresponding `/enable` API or UI, then verify the schedule, SHA and command. Preserve concurrency group `whoop-briefing`, `cancel-in-progress: false` and hourly `17 * * * *`.
4. The checked-in Render Blueprint declares a **free** web service. Render maintenance mode is paid-only. The Render API supports `POST /v1/services/{serviceId}/suspend` and `/resume`, but deploy hooks reject a suspended service. A safe free-tier writer-quiescence and release replacement sequence therefore needs live-service inspection before approval. If the actual service is paid, maintenance mode can block public ingress while the service stays running; disable GitHub and Cloudflare first, then wait for in-flight work to drain, migrate, deploy the v31-compatible release, and remove maintenance mode only after verification. Do not resume an old v20 service binary against v31. If the service is free, establish a verified alternative such as a new v31-compatible service while the old one remains suspended, then move ingress only after the new service is healthy. Do not assume settings updates on a suspended service deploy a new binary.
5. Use Turso management access to verify account/database identity, region, branch creation, retention/PITR and restore/repoint rights. A database bearer token proves SQL access only. If branch creation permission cannot be established read-only, record `BACKUP_CREATE_PERMISSION_REQUIRES_LIVE_CAPABILITY_TEST`; the final deployment needs a separately approved branch creation before any migration.

## Default-branch workflow transition

The release-branch workflow is intentionally not treated as an active schedule because GitHub schedules run from the default branch. The main-branch transition artifact must checkout the literal reviewed RC commit SHA, use Node 22 and `npm ci`, and run `node src/publicBetaEntry.js` with the Phase 4/Beta environment names. The SHA is filled **after** the deployment-control review, so no mutable branch can silently become the runtime. Apply the artifact to `main` only during the separately authorized final deployment, while the workflow is disabled. The old `main` workflow must never resume against v31.

Before activation: `PHASE4_BETA_SHADOW_RUNTIME=off`, `PHASE4_PUBLIC_BETA_MODE=off`, `PHASE4_PUBLIC_BETA_USER_IDS` empty. Activation requires stable `PHASE4_LOOKUP_KEY` and `PHASE4_AUDIT_KEY`, `PHASE4_BETA_SHADOW_RUNTIME=on`, `PHASE4_PUBLIC_BETA_MODE=allowlist`, and only approved canonical user IDs in `PHASE4_PUBLIC_BETA_USER_IDS`. LIVE remains rejected. Select zh-TW, en and vi through the real locale flow on three READY controlled users; do not fabricate a Beta Summary when no current approved item exists.

Rollback keeps the v31-compatible reviewed release tree, sets presentation OFF and then SHADOW runtime OFF, and never downgrades the schema or returns to the v20 `main` binary.
