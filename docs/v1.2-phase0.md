# V1.2 Phase 0：正式環境觀測基線

Phase 0 **不是**架構遷移，也不是 V1.2 Phase 1。它只做一件事：

> 讓 V1.1 正常跑 7～14 天，蒐集真實行為的證據，讓 V1.2 的決定建立在資料上而不是假設上。

期間**不要**改排程、不要開 webhook、不要動同步語義、不要改分析門檻。

---

## 指令

```bash
npm run phase0
```

只讀 Turso。它**不會**：打 WHOOP、打 OpenRouter、送 Telegram、跑 migration、
寫健康資料、動 report claim、改排程狀態。輸出裡沒有任何生理數值，也沒有任何 token 值。

（`npm run health-status` 仍然是日常的健康檢查；`phase0` 專門看 V1.2 要的那幾條時間鏈。）

---

## 時間戳的語義（讀輸出之前先搞清楚）

| 欄位 | 是誰的時間 | 意思 |
|---|---|---|
| `whoop_*.created_at` | **WHOOP 的** | WHOOP 建立這筆紀錄的時間 |
| `whoop_*.updated_at` | **WHOOP 的** | WHOOP 最後一次改這筆紀錄的時間 |
| `whoop_*.synced_at` | **我們的** | 最後一次寫進 Turso 的時間 |

所以：

- `updated_at > created_at` ⇒ WHOOP 的「最後更新時間」晚於「建立時間」。這可能包含初次評分或後續修訂，
  **不能單憑當前一列證明我們觀測過多個版本**
- `synced_at` 在每次 upsert 都被覆寫 ⇒ 它是「最後一次同步」，**不是「第一次落地」**

凡是由這些推導出來的延遲，輸出都標成 `（推論）`。我們沒有觀測到「WHOOP API 何時
第一次可以拿到這筆資料」這個事實 —— 不要把推論當成觀測。

命令輸出的時間戳一律顯示為 **UTC**；`health_date` 則是使用者時區的當地日期。

## 觀測計畫

### Day 0（今天）
- 跑一次 `npm run phase0`，把輸出存起來當起點。
- 確認排程器心跳存在、token 有綁定、同步五個 resource 都有 `最後成功`。
- 之後就**讓它自己跑**。

### Day 3 — 早期健檢（只看有沒有壞掉，不下結論）
- 心跳有沒有持續更新？
- 有沒有 resource 卡在 `last_error`？
- 每日報告有沒有正常送出（認領數 == 送出數）？
- 有問題才介入；沒問題就不要動它。

### Day 7 — 第一次有意義的基線回顧
逐項看：
- 累積了幾組真實的「主睡眠 + 恢復」？
- `結束→WHOOP更新` 的分布長什麼樣？（這是 WHOOP 評分的速度）
- `WHOOP更新→最後同步`與`有資格→送出`的推論分布？前者不是首次 API 可用→首次落地，
  只能當方向性線索，不能單獨用來證明 webhook 效益。
- 修訂比例多高？修訂發生在多久之後？
- token 的最後寫入與到期時間為何？要證明 refresh 真的發生，必須另引 Actions log；
  `updated_at` 本身不能分辨初次授權或 refresh。
- Telegram worker 有沒有處理過訊息？

如果證據已經足夠回答下面的「離開條件」，就可以進 Phase 1。

### Day 14 — 只在 Day 7 證據不足時才需要
特別是：如果 7 天內**完全沒有觀察到修訂**，那本身就是一個結論
（「這個帳號的資料很穩定」），要明確寫下來，而不是繼續等。

---

## 離開 Phase 0 的最低條件

- [ ] 多組真實的主睡眠／恢復配對（不是只有一天）
- [ ] 多個排程週期的證據
- [ ] 至少一次有 Actions log 佐證的真實 token refresh（不只看 token `updated_at`）
- [ ] 足夠的同步執行次數，看得出正常的時間分布
- [ ] 對 WHOOP 修訂行為有結論 —— 要嘛看到修訂，要嘛**明確記錄「這段期間沒有觀察到修訂」**
- [ ] 每日報告的時間證據
- [ ] Telegram worker 的運作證據
- [ ] 基本的成本／API 用量證據
- [ ] 沒有未解決的 Critical 可靠性問題

**不要**為了拖延 V1.2 而要求一個很大的樣本數。夠回答問題就夠了。

---

## 這些證據要餵給哪些 V1.2 決定

| 決定 | Phase 0 提供的證據 |
|---|---|
| 1. 要不要上 webhook | `WHOOP更新→最後同步`、`有資格→送出` 的推論分布，連同 Actions log 與已知量測缺口評估；不把前者當成首次落地時間。 |
| 2. 對帳頻率 | 排程可靠度、修訂發生的時間點、遲到資料的頻率、API 用量 |
| 3. 增量同步視窗 | 修訂多常發生、往回多遠、目前的 API 用量輪廓 |
| 4. 攝取與分析要不要拆開 | 重要事件的延遲、目前分析的耗時與成本、完整分析真正有用的頻率 |
| 5. Proactive Intelligence V2 | readiness 穩定度、alert 頻率、低價值事件的樣態、缺脈絡的機會點 |

**Phase 0 不實作以上任何一項。**

## 已知量不到的東西（以及為什麼不補）

| 量不到 | 為什麼 |
|---|---|
| 第一次落地時間 | `synced_at` 每次 upsert 被覆寫。補它要改 upsert 行為 —— Phase 0 明確禁止。 |
| WHOOP API 可用時間 | 我們沒有觀測到這個事實。只能用 WHOOP 自己的時間戳當推論。 |
| 修訂次數／修訂觀測時間 | upsert 就地覆寫、沒有歷史列。要補就要加表 —— Phase 0 避免 schema 變更。 |
| `score_state` 轉換時間 | 只存目前狀態，沒有 PENDING→SCORED 的轉換點。 |
| token refresh 事件 | token `updated_at` 只證明 token 列被寫入，無法區分初次授權或 refresh；需要 Actions log 佐證。 |
| 排程器歷次執行 | `system_heartbeats` 是單列覆寫，只留最後一次。漏跑／重跑的歷史在 GitHub Actions 的 run 紀錄裡，不在 DB。 |
| 每次同步的筆數與耗時 | 只在執行當下的 log，沒有持久化。 |
| Telegram worker 心跳 | 目前只有 `cron` 這個 component 有心跳，worker 沒有 → 它掛掉不會留下痕跡。 |

這幾項如果在 Phase 1 被證明真的需要，再用**一次**有意識的 schema 變更補齊，
而不是在觀測期間偷偷改動正在被觀測的系統。

---

## 注意：排程器診斷由另一個任務負責

Phase 0 **只讀**排程器的心跳，不碰任何 workflow 設定、不 dispatch、不改節奏。
如果心跳落後期望節奏很多，那屬於排程診斷的範圍，不要在 Phase 0 裡順手修。
